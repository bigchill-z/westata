release: record that 0.0.1 went to PyPI by accident, and ship the sdist manifest that made it complete

Two things, both about making the published artefact and the repository agree.

1. MANIFEST.in now includes the Chinese docs and the comparison data

   The sdist published to PyPI was built after this change but the change itself was never committed,
   so the repository described a narrower source distribution than the one that actually shipped. It
   was uncommitted at the moment of upload: 159 entries, including README.zh-CN.md,
   docs/GUIDE.zh-CN.md, docs/comparison.json and the three data CSVs. Committing it is what makes a
   fresh clone reproduce the published sdist.

2. CHANGELOG records how 0.0.1 was released

   0.0.1 went to the real PyPI channel while the intent was to exercise TestPyPI: the token in hand
   belonged to pypi.org, not test.pypi.org, so twine authenticated and uploaded for real. The worse
   part is that after the first 403 the operator retried against the production endpoint as an
   "authentication probe" -- twine has no dry-run, so every call is an upload.

   The version number is permanently spent, because PyPI does not allow deleting or overwriting. The
   content itself is sound: the README opens with the measured deviation table, the licence and
   dependency declarations are complete, 1455 tests pass and CI is green on three Python versions.
   So 0.0.1 stays and future work goes to 0.0.2.

   Recorded in the changelog rather than left implicit, because a release log should say how a version
   got out. Someone later looking at a first release numbered 0.0.1 with no tag history should not have
   to guess. It doubles as a process note: do not call twine with a real token before confirming the
   target channel.
