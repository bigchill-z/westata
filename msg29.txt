docs: the install instructions described the world before the release

0.0.1 is on PyPI with both artefacts, but four documents still said "not on PyPI yet, install from
the repository". That is no longer a cautious phrasing, it is a false statement of fact: it sends a
reader to clone a repo when `pip install westata` works.

Changed to the published path, with the source install kept as the route for working on the library
itself. Both were verified before writing:

    pip install westata            -> 0.0.1
    pip install "westata[arch]"    -> arch 8.0.0 + westata 0.0.1

Files: README.md, README.zh-CN.md, and BOTH guides. The guides are generated, so the fix went into
docs/generate_guide.py and docs/gen_guide_zh.py as well -- editing only the artefacts would have been
overwritten on the next regeneration, which is a mistake this project has already made once with the
observation-count section.

ALSO ADDED: tests/test_release_state.py, which asks PyPI rather than grepping strings

    if the package is published, no document may claim it is not
    if it is published, every document must show `pip install westata`
    pyproject's version may lead the newest published one but never lag it

The check derives its expectation from the network rather than from a constant, so it keeps working
after 0.0.2 or 0.1.0 without anyone updating the test. It skips when pypi.org is unreachable, because
a network failure should not fail a build.

FOUND WHILE DOING THIS, and not fixable by editing: the PyPI page for 0.0.1 still shows the old text.
PyPI freezes the description into the uploaded metadata, so the only way to correct that page is a new
version. Hence 0.0.2.
