CHANGELOG.md
    Covers the whole history, because 0.0.1 is a first release and has no predecessor to diff against. The known
    limitations get a TOP-LEVEL section with the same emphasis as the features, with per-command numbers and
    reasons. A changelog that lists only features trains readers to skim it, and these nine entries are the most
    decision-relevant thing in the repository.

FOUND WHILE DOING THIS: the test suite implicitly required the optional `arch` dependency

    A clean install without `arch` reported:
        7 failed, 1427 passed
    every failure being `UnsupportedError: ARCH/GARCH estimation needs the optional arch dependency`.

    The library was behaving correctly -- that is the error message added in the packaging round, firing exactly
    where designed -- but the TESTS were wrong: a test for a feature whose optional dependency is absent should
    SKIP, not fail. A CI reporting 7 failures on a clean install reads as "the package is broken", and the
    obvious fix would be to make `arch` mandatory, which is the outcome the optional split exists to prevent.

    My first pass decorated five tests by grepping the IMPLEMENTATION for `from arch import ...`, and missed two:

      * test_garch_rejects_unknown_cov_type_and_presample -- I reasoned it asserts on our own validation, which
        runs before the import. Half right: the cov_type rejection does come first, but the test also exercises
        presample="stata", which reaches the fit and therefore the import.
      * test_pperron_default_bandwidth_follows_newwey_west -- it lives in tests/conformance/, so scanning the file
        where the PP implementation sits never saw it.

    The correct procedure is the reverse of what I did: run the suite WITHOUT the optional dependency and let the
    failures name the tests. Both configurations are now clean:

        with arch       1439 passed
        without arch    1427 passed, 7 skipped, 0 failed

MANIFEST.in, and a BOM that broke the build for the second time
    setuptools left CHANGELOG.md out of the sdist. Adding MANIFEST.in did not help -- because
    `Set-Content -Encoding utf8` had prepended EF BB BF, so the first line read "\ufeffinclude CHANGELOG.md" and
    the directive was silently unrecognised. The build succeeded, twine passed, and the file was simply absent.

    The same BOM had already broken pyproject.toml two commits ago, where TOML rejected it loudly. This time it
    failed quietly, which is what makes it worth a test: a loud failure self-corrects, a quiet one ships.

    tests/test_packaging_hygiene.py now checks the packaging files for a BOM at the BYTE level (read_text with
    utf-8 leaves it in the string while utf-8-sig strips it, and the consuming tools do the former), asserts the
    manifest names the changelog and licence, and pins the three required runtime dependencies plus `arch`
    staying an extra -- the last being a regression guard for the unimportable-wheel defect.
