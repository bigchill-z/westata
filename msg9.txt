feat(nbreg): implement dispersion(constant) — Stata's NB1 — from nbreg_al.ado

The gap was `TypeError: _DiscreteBase.fit() got an unexpected keyword argument 'dispersion'` with a diagnostic
note saying the model was "well-posed, not implementable". It is now implemented and measured: coefficients
2.93e-09, standard errors 3.40e-10, log-likelihood 1.21e-16 against a live Stata.

THE PARAMETERISATION IS THE WHOLE PROBLEM, and I got it wrong first. `nbreg_al.ado` lines 19-30:

    xb     = b0 + x b
    mu     = exp(xb)
    m      = exp(xb - lndelta)      <- NOT mu. This is mu/delta.
    delta  = exp(lndelta)
    lnoned = log1p(delta)           <- not log1p(exp(lndelta)); equal in exact arithmetic, better conditioned

    lnf = lgamma(y + m) - lgamma(y+1) - lgamma(m) + lndelta*y - (y + m)*lnoned

My first version used `mu` in place of `m`. That still converges, still reports plausible coefficients, and fits
a different model. It was caught by comparing the likelihood at STAT'S estimates rather than at our own: with
the wrong parameterisation the likelihood there was -947.25 against Stata's -936.95, a 1e-2 gap, while at our
own estimates it looked fine. Comparing a likelihood only at your own optimum is a test that can pass by luck.

A SECOND ERROR followed from the same carelessness about which scale is which. Stata reports

    /lndelta   -.2037068   .1614197        <- in e(V), on the log scale
    delta       .8157015   .1316703        <- displayed separately, delta-method SE

I applied the delta-method Jacobian to `e(V)`, which put delta's SE (0.1317) under the /lndelta name and made
that standard error 18.4% wrong. `e(V)` now stays on the lndelta scale and `e(delta)`'s SE is reported
separately as `e(sedelta)`.

WHY A SEPARATE CLASS rather than `dispersion=` on NegativeBinomial: NB1 and NB2 differ in the likelihood, in
what the dispersion parameter means (delta against alpha) and in the variance function. A flag would push that
branch into the score, the information, the naming, the rescaling and the reported scalars -- five places to
miss one, each of which silently returns NB2 numbers under an NB1 label.

THE SWEEP SCRIPT AGAIN ASSERTED THE GAP, the third such block in three rounds. It called
`NegativeBinomial.fit(dispersion="constant")` inside a `try` whose `except` recorded the error, so after the
implementation landed it would have kept reporting a gap. Now it compares. Three occurrences of the same shape
is a pattern, not a coincidence: a conformance script that encodes "not implemented" preserves that claim
indefinitely, and these blocks should be reviewed wholesale rather than noticed one at a time.

tests/test_nb1.py pins the fit, the likelihood at a shared point, the score against a numerical gradient, the
scale separation, and the fact that NB1 and NB2 are materially different fits -- so collapsing them into one
class with a flag fails a test instead of shipping.

Sweep totals: error rows 6 -> 5. Suite: 1420 -> 1425 passing.
